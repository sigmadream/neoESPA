# neoESPA Development Plan

- 기준 문서: `refs/prd.md`
- 기준일: 2026-03-25
- 문서 목적: PRD의 `완료 / 계획 / 발전 단계`를 실제 구현 순서, 작업 묶음, 검증 기준으로 분해한다.

## 1. 계획 원칙

- 모든 구현은 `refs/prd.md`의 `PRD-*` 요구사항을 기준으로 추적한다.
- 문서의 공식 분류는 `완료 / 계획 / 발전 단계`를 따른다.
- 이 문서에서 쓰는 실행 순서는 우선순위와 묶음 설명용이며, 제품 단계 분류를 대체하지 않는다.
- 이미 있는 API와 도메인을 가능한 한 확장하고, 필요 이상의 재작성은 피한다.
- 각 작업 묶음은 `구현 + 검증 + 운영 반영 기준`이 모두 충족되어야 완료로 본다.

## 2. 현재 상태 요약

- **완료**: 인증, 프로필 수정/비밀번호 변경, 과제 목록·상세·제출·결과, 학생 대시보드, 공지, 링크형 강의자료, 알림, 관리자 콘솔, 자동 채점/재채점/export, 협업, 시험 API
- **계획**: 시험 전용 UI, 게시판형 자료실, 게시판형 Q&A, 코스 허브, 상세 채점 결과 강화, 린트 parity UI, 표절 판정 후속 흐름, 멤버십 상태/승인 흐름
- **발전 단계**: offering 기반 멀티 코스 구조, 외부 연동, 운영급 실행기/스토리지/복구 하드닝

## 3. 실행 묶음

이 섹션은 새 PRD의 단계 구분을 실제 개발 순서로 풀어쓴 것이다. 즉, 공식 단계명은 `계획 / 발전 단계`를 따르고, 아래 `실행 묶음`은 구현 순서를 설명한다.

### 3.1 계획 실행 묶음 A — 학생 경험 공백 해소

목표: 학생이 별도 우회 없이 수업 핵심 흐름을 한 제품 안에서 끝낼 수 있도록 현재 UX 공백을 닫는다.

대상 요구사항:

- `PRD-04`, `PRD-07`, `PRD-09`, `PRD-11`

주요 작업:

1. 시험 전용 학생 UI 구현
2. 코스 허브 화면 구성
3. 상세 채점 결과와 전용 린트 뷰어 보강
4. 게시판형 제출 구조와 현재 homework 흐름의 연결 방식 정리

완료 기준:

- 학생이 시험, 과제, 결과, 공지/자료 진입을 하나의 제품 경험 안에서 사용할 수 있다.
- 결과 화면이 총점 외에도 충분한 설명성과 피드백을 제공한다.

### 3.2 계획 실행 묶음 B — 운영 도구 공백 해소

목표: 운영자가 현재 관리자 콘솔만으로 수업 운영에 필요한 세밀한 제어를 수행할 수 있도록 한다.

대상 요구사항:

- `PRD-06`, `PRD-08`, `PRD-10`

주요 작업:

1. 게시판형 자료실 구현
2. 게시판형 Q&A와 댓글/첨부 흐름 구현
3. 린트 `Score`, `Option`, `Message`, `Rule` parity UI 구현
4. 표절 판정, 메모, 점수 반영, 감사 로그 연결 흐름 구현

완료 기준:

- 운영자가 링크형 자료 관리 수준을 넘어 게시판형 운영 도구를 사용할 수 있다.
- 린트 정책 관리가 현재 일부 settings 편집 수준을 넘어 레거시 운영 요구를 충족한다.
- 표절 운영이 탐지/비교를 넘어 판정 가능한 흐름으로 닫힌다.

### 3.3 계획 실행 묶음 C — 계정 정책 보강

목표: 현재 단일 계정 기준선 위에 멤버십 상태와 운영 승인 흐름을 보강한다.

대상 요구사항:

- `PRD-02`

주요 작업:

1. 멤버십 상태 모델 정의
2. 승인/전환 정책 정리
3. 상태 확인과 운영 처리 UI/API 보강

완료 기준:

- 프로필 수정과 비밀번호 변경을 넘어 멤버십 상태 운영이 문서와 화면 기준으로 정리된다.

### 3.4 발전 단계 실행 묶음 A — 멀티 코스와 외부 연동

목표: 단일 강좌 구조를 학기/분반/offering 및 외부 시스템 연동 구조로 확장한다.

대상 요구사항:

- `PRD-13`, `PRD-14`

주요 작업:

1. `courses`, `terms`, `course_offerings`, `course_enrollments` 도입
2. 과제, 공지, 자료, 시험, 게시판의 offering 스코프 적용
3. offering 기반 권한 모델 정리
4. LMS roster sync 및 grade export 연동
5. SSO, 외부 identity, 소셜 로그인 연동

완료 기준:

- 하나의 제품이 여러 학기/분반을 충돌 없이 운영한다.
- 외부 명부/성적 연동이 offering 단위로 동작한다.

### 3.5 발전 단계 실행 묶음 B — 운영급 하드닝

목표: 현재 개발/수업 운영 기준 실행기와 저장 구조를 운영급 기준으로 강화한다.

대상 요구사항:

- `PRD-15`, `PRD-16`

주요 작업:

1. 컨테이너 기반 채점 샌드박스 도입
2. 실행 메타데이터와 자원 사용량 기록
3. 외부 객체 스토리지 기반 제출 파일 저장
4. 운영 경보와 복구 리허설 자동화

완료 기준:

- 채점 실행이 자원 제한과 격리 기준을 충족한다.
- 백업/복구와 장기 저장 정책이 운영 절차로 정착한다.

## 5. 세부 실행 백로그

### 5.1 완료 유지 항목

- 인증, 권한, 과제 제출, 공지/자료/알림, 관리자 콘솔, 협업, 시험 API에 대한 회귀 테스트 유지
- 관리자 API와 현재 프론트엔드 화면 사이의 계약 불일치가 생기지 않도록 문서/API/테스트를 함께 관리

### 5.2 계획 백로그 — 학생 경험

- 시험 목록/응시/결과 화면 구현
- 코스 허브 요약 카드와 진입 구조 설계
- 결과 화면의 테스트케이스별 결과, 로그, 패널티 근거 강화
- 전용 린트 뷰어와 주차 가이드 구현
- 게시판형 제출 메뉴와 현재 과제 모델 매핑 정리

### 5.3 계획 백로그 — 운영 도구

- 게시글, 댓글, 첨부, 카테고리 공통 도메인 설계
- 자료실 게시판 API/UI 구현
- 질문과 답변 게시판 API/UI 구현
- 점수 설정 UI
- 옵션 설정 UI
- 메시지 번역 관리 UI
- 주차 템플릿 규칙 UI
- 표절 판정, 점수 반영, 메모, 감사 로그 흐름 구현

### 5.4 계획 백로그 — 계정 정책

- 멤버십 상태 모델 정의와 승인 정책 반영
- 기존 게시판 계정/준회원 흐름의 전환 정책 정리
- 학생/운영자 권한 경계 테스트 보강

### 5.5 발전 단계 백로그

- offering 스키마와 스코프 분리
- LMS adapter와 grade export 연동
- SSO/provider adapter
- 격리 실행기, 스토리지 adapter, 경보 자동화
- authoritative source, 수동 재동기화, 장애 시 운영자 복구 절차 정의

## 6. 검증 전략

### 6.1 자동 검증

- 백엔드: 관련 API, 권한, 상태 전이, 저장 로직에 대한 `pytest`
- 프론트엔드: 핵심 학생/운영자 흐름에 대한 Playwright E2E
- 릴리스 전: lint, build, 주요 시나리오 재실행

### 6.2 단계별 검증 기준

- **완료 유지**: 현재 완료 기능의 회귀가 없어야 한다.
- **계획**: 학생/운영자 화면 기준으로 실제 사용 가능한 흐름이 닫혀야 한다.
- **발전 단계**: 구조 확장과 운영 하드닝이 기존 단일 코스 기준선을 깨지 않아야 한다.

### 6.3 영역별 검증 기준

- 계정: 가입 정책, 중복 `sid`, 이메일 형식, 권한 제한, 멤버십 상태 전이 검증
- 게시판: 목록/상세/작성/수정/삭제/첨부/댓글 검증
- 채점 결과: 케이스별 결과, 로그, 패널티, 품질 점수 노출 검증
- 린트 운영: 설정 변경 후 채점 결과에 실제 반영되는지 검증
- 시험/표절: 운영자 액션 이후 학생/운영자 화면과 감사 로그 일관성 검증
- 멀티 코스: offering 간 데이터 격리와 권한 경계 검증
- 운영 안정성: 백업 복구 후 로그인, 과제 조회, 제출 조회, export 정상 동작 검증

## 7. 의존성과 리스크

- 게시판 공통 도메인을 먼저 정리하지 않으면 자료실과 Q&A 구현이 중복될 가능성이 높다.
- offering 모델 없이 LMS/SSO를 먼저 붙이면 재작업 위험이 크다.
- 린트 parity는 `supportFiles/` 구조와 관리자 UX를 동시에 맞춰야 하므로 백엔드/프론트엔드 결합도가 높다.
- 샌드박스 하드닝은 인프라 제약과 배포 환경 결정을 선행해야 한다.

## 8. 권장 구현 순서

1. 시험 UI, 코스 허브, 상세 채점 결과 보강
2. 게시판 공통 도메인 설계
3. 자료실/Q&A 구현
4. 린트 parity UI
5. 표절 후속 워크플로
6. 멤버십 상태/승인 흐름
7. offering 기반 멀티 코스 구조
8. LMS/SSO 연동
9. 운영급 샌드박스와 외부 스토리지
